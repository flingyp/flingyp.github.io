# 分享一下25年我日常常用需求迭代的 Vibe Coding 方法

> 在需求明确的情况下使用，不然变成屎山代码也别怪 AI 垃圾，怪人。

日常需求迭代主要用 Claude + GLM/Kimi/deepseek 很便宜，至少能减少现有项目 70% 80% 重复工作型的开发任务

需求开发模版文件 `INITIAL.md`

```markdown
## Feature

## Documentation

## Tips

- 修改过的文件中添加注释 `TODO: ${需求名称}-开发中` 字样（logs 文件夹下文件除外）
- 功能实现如依赖第三方插件，请使用 PNPM 包管理工具。
- 无需过多考虑功能的完整性
  - 如果需要额外添加需求未提到的功能
  - 请先询问我获取我的同意，在进行扩展
- 无需修复导入顺序和类型导入的问题。
  - 在修复其问题如果出现长期无法修复的问题
  - 需要在文件中标志注释 `TODO: 类型问题-待修复` 即可，然后跳过类型修复问题
- 需求功能开发后后都需要在当前标题标注【已完成】
- 最后需求完成后，总结一份日志报告。
  - 要整体描述需求/BUG，以及需求功能的实现或BUG修复内容，以及修改的文件路径和描述具体改了什么。
  - 输出报告至 `logs` 文件夹中，文件名为：`${YYYYMMDD}-${需求名称}.md`
```

- `@developemnt/xxx 开发需求`
- 带着需求，进行第一轮对话。如果在这一轮之内，三轮对话没有完成需求，直接重开一个 Claude Code 窗口
- 带着文档、log 日志报告，继续开发，确保需求完成。

之后的任务都最好指定让它同步更新日志报告。

- `@developemnt/xxx 开发需求任务，最后同步日志报告文档 @logs/xxx`
- 完成需求后，自己 review 一下，确保没有问题，下一步就是优化代码。
- 让它自己总结改动的代码是否整洁，是否可以复用。让它自己优化代码，最后同步更新日志报告

最后搭配一个 Claude Skill，移除所有需求的 TODO 注释

```markdown
---
name: remove-todo
description: 删除指定需求的TODO 注释，在确认需求完成之前。
---

# 删除指定需求 TODO 注释

1. 查找当前项目下所有带有 【指定需求 TODO 注释】 的文件
2. 批量删除这些文件的 TODO 注释
```
